# Enterprise AI Analyst — Technical Interview Defense & Architectural Evidence Guide

This document provides concrete engineering evidence, architectural rationale, and verifiable test references for technical discussions and architecture reviews.

---

## 1. Multi-Tenancy & Tenant Isolation

* **Core Question**: *"How do you guarantee that Tenant A's private data is never leaked or mixed with Tenant B's data under high concurrency?"*
* **Architectural Defense**:
  1. **Strict Context Injection**: Every request passes through `TenantContextMiddleware` which extracts and validates the tenant ID from the authenticated JWT token.
  2. **Row-Level Security (RLS) & Filter Enforcement**: All SQL queries and vector searches mandate `organization_id` in their predicates (`WHERE organization_id = :org_id`).
  3. **Isolation Verification Test**: In `tests/e2e/test_load_and_performance.py::test_tenant_load_isolation`, 50 burst requests from `Tenant A` were executed alongside `Tenant B` requests. Zero cross-tenant records or attribution leaks were observed.
* **Code References**:
  - `backend/app/tenancy/context.py`
  - `backend/tests/finops/test_tenant_isolation.py`
  - `backend/tests/e2e/test_load_and_performance.py`

## 2. Hallucination-Resistant RAG Architecture

* **Core Question**: *"How does the system ensure LLM responses don't hallucinate facts not present in uploaded documents?"*
* **Architectural Defense**:
  1. **Hybrid Retrieval**: We combine dense vector similarity (cosine) with sparse BM25 lexical search using Reciprocal Rank Fusion (`app/retrieval/hybrid/rrf.py`).
  2. **Cross-Encoder Reranking**: The merged top-K candidates are scored by a cross-encoder model to filter out irrelevant chunks.
  3. **Strict Citation Contract**: Answers must link specific claims to citations (`[S1]`, `[S2]`).
  4. **Hallucination Verification Gate**: The synthesized answer is evaluated against retrieved evidence before streaming completion. If ungrounded claims exceed the tolerance threshold, the response is flagged or regenerated.
* **Code References**:
  - `backend/app/rag/service.py`
  - `backend/app/rag/grounding.py`
  - `backend/tests/e2e/test_rag_flow.py`

## 3. Secure Text-to-SQL Execution

* **Core Question**: *"How do you prevent malicious SQL injection or destructive queries like DROP TABLE or data exfiltration via LLM?"*
* **Architectural Defense**:
  1. **Semantic Layer Abstraction**: Natural language maps to vetted metrics and dimensions in `app/semantic/`, preventing raw table exposure.
  2. **AST SQL Parser**: Queries generated by the LLM are parsed into an Abstract Syntax Tree. Only `SELECT` and `WITH` statements are permitted. `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `EXEC` are rejected before hitting the database.
  3. **Execution Guardrails**: Read-only database transaction, 5-second statement timeout, and strict row limit (default: 1000 rows).
* **Code References**:
  - `backend/app/sql_agent/service.py`
  - `backend/app/sql_agent/providers/`
  - `backend/tests/e2e/test_sql_flow.py`

## 4. Multi-Agent Orchestration & State Recovery

* **Core Question**: *"What happens if a long-running agent task crashes mid-execution? Can it resume?"*
* **Architectural Defense**:
  1. **Finite State Machine**: The agent lifecycle is governed by an explicit FSM: `CREATED -> PLANNING -> EXECUTING -> CHECKPOINTED -> EXECUTING -> COMPLETED`.
  2. **Durable Checkpoints**: Tool execution results and memory states are persisted to PostgreSQL checkpoints after each step.
  3. **Budget & Loop Bounds**: Maximum step counts and cost caps prevent runaway infinite loops.
* **Code References**:
  - `backend/app/agents/runtime.py`
  - `backend/app/agents/checkpoints.py`
  - `backend/tests/e2e/test_agent_flow.py`

## 5. Enterprise FinOps & Cost Governance

* **Core Question**: *"How do you prevent unexpected cloud AI bills, and how is cost accurately tracked?"*
* **Architectural Defense**:
  1. **Append-Only Usage Ledger**: Every LLM call records a `CostEvent` with token breakdowns (prompt, completion, cached) and calculated costs down to `Decimal(12, 4)` precision.
  2. **Versioned Pricing Registry**: Effective-dated model pricing registry (`ModelPricing`) prevents historical accounting retroactive distortion.
  3. **Preflight Budget Enforcement**: Budgets evaluate burn rates and reject calls with `BUDGET_EXCEEDED` before provider dispatch when 100% hard limit is reached.
  4. **Precedence Rule**: `Security > Quality Floor > Reliability > Cost`. Cost optimization never routes sensitive data to unapproved providers or breaches quality thresholds.
* **Code References**:

## 6. SRE, Chaos Engineering & Release Gates

* **Core Question**: *"How do you prevent broken releases from hitting production, and how do you handle upstream LLM outages?"*
* **Architectural Defense**:
  1. **Multi-Window Multi-Burn Alerts**: Evaluates SLO consumption over 1h, 6h, and 3-day windows to detect critical burns before total budget exhaustion.
  2. **Automated Incident State Machine**: Incidents transition through `DETECTED -> INVESTIGATING -> MITIGATING -> RESOLVED -> CLOSED`.
  3. **Automated Release Gates**: `evaluate_release_safety` blocks releases if SLO error budgets are depleted, critical security findings exist, or budgets are exhausted.
* **Code References**:
  - `backend/app/sre/gates.py`
  - `backend/app/sre/alerts/`
  - `backend/tests/unit/test_sre_runbooks_and_gates.py`
  - `backend/tests/e2e/test_release_gate_flow.py`
